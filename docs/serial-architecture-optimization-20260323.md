# 串口通讯架构优化说明 2026-03-23

## 目标

在不改变现有 `0x03 / 0x06 / 0x10` 二进制协议业务处理逻辑的前提下，完成以下优化：

- 收敛 `SCI1` / `SCI2` 重复的收发状态机代码
- 接入 `ascii_slave.c` 协议，并与现有协议兼容共存
- 为两类协议统一增加接收超时清帧机制
- 保留原有外部函数入口，避免主流程和中断调用点大范围改动

## 本次改动

### 1. 统一串口端口上下文

在 [Sci_Upper.c](/E:/TODO/030%20+%20309/Code/Source/Sci_Upper.c) 中新增串口端口上下文 `SCommonUpperPort`，统一维护：

- `USART` 实例
- `RS485MSG` 协议状态
- 错误计数、发送使能、发送完成标记
- ASCII 接收缓冲
- 当前协议类型
- 接收超时计数

`Sci1_CommonUpper_*` 和 `Sci2_CommonUpper_*` 这两套旧接口仍然保留，但已经退化为对公共实现的薄封装。

### 2. 统一协议入口分流

公共接收入口现在按首字节和当前上下文状态分流：

- 首字节为 `0x7E` 时，进入 ASCII 协议接收
- 其他情况沿用原有 RS485 二进制协议接收

这样做的前提是现有 RS485 从机地址为 `0x00 / 0x01`，与 ASCII 帧头 `0x7E` 不冲突，因此可以安全共存。

### 3. 把 `ascii_slave.c` 改为可复用解析模块

[ascii_slave.c](/E:/TODO/030%20+%20309/Code/Source/ascii_slave.c) 去掉了原先的全局接收状态：

- `uart_rx_buf`
- `uart_rx_len`
- `frame_received_flag`

`Frame_Parse_Process()` 改为显式接收：

- 接收缓冲指针
- 接收长度
- 当前串口实例

同时移除了对 `UART1` 的硬编码，ASCII 协议现在可以按调用端口回包。

### 4. 增加统一超时机制

新增两类超时：

- RS485 半包超时：`20ms`
- ASCII 半包超时：`50ms`

超时处理挂到系统 1ms 周期函数 [bsp.c](/E:/TODO/030%20+%20309/Code/Source/BSP/bsp.c) 的 `bsp_RunPer1ms()` 中，通过 `CommomUpper_1msTick()` 驱动。

超时后的处理策略：

- ASCII：丢弃当前半包，清空 ASCII 接收状态
- RS485：复位当前端口消息状态，恢复接收能力

## 兼容性说明

- 现有 `App_CommonUpper()`、`InitUSART_CommonUpper()`、中断入口和 `Sci1_*/Sci2_*` 名称未变
- `Sci_Deal_*`、`Sci_ACK_*`、各类寄存器读写处理函数未改业务语义
- ASCII 协议解析和回包格式未改，只改为按端口参数工作

## 风险与取舍

- 为了让两个串口都能独立兼容 ASCII，本次给每个端口增加了一份 ASCII 接收缓冲，代码体积下降的同时会带来一定 RAM 增量
- 当前环境没有可用的 `armcc` / `clang` / `gcc`，本次无法做编译和新的 `map` 实测
- `SCI2` 发送路径原实现和 `SCI1` 存在细节差异，本次已统一到一套发送骨架，仍建议在目标环境做串口联调验证

## 建议验证项

1. `SCI1` 原有上位机协议读写是否保持正常
2. `SCI2` 原有上位机协议读写是否保持正常
3. ASCII 协议在 `SCI1`、`SCI2` 上是否都能独立收发
4. 故意发送半包后，`20ms/50ms` 超时是否能恢复后续正常通讯
5. 重新生成 `map`，确认 `sci_upper.o` 的代码段是否继续下降
