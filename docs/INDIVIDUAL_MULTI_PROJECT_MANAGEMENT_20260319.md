# 个人多项目 / 多客户 / 多版本管理方案

## 目标

这份文档专门面向你当前的真实工作方式，而不是通用团队流程。

你的典型场景是：

- 一个人维护很多项目
- 项目大逻辑类似，但 `MCU / AFE / IO / BSP` 不同
- 每个项目通常同时存在：
  - 稳定出货版本
  - 长期重构 / 新研发版本
  - 热修复版本
- 一个项目还会派生出多个客户差异版本

这类场景最怕的不是“不会写代码”，而是：

- 共性逻辑无法复用
- 客户差异散落在源码里
- 热修复没有回流
- 稳定版和研发版越走越远
- 改一个客户把另一个客户带崩
- 只能靠你脑子记住分支和差异

这份方案的目标就是把这些风险收敛成 Codex 可接管的管理结构。

## 核心原则

你后面不应该再按“一个客户复制一份代码，各自演化”的方式长期维护。

更适合你的结构是：

- 共性逻辑一套
- 硬件差异单独隔离
- 客户差异配置化
- 版本线固定化
- 回归入口统一化
- Codex 负责第一轮实现、检查、审查、总结

一句话概括：

**共性归核心，差异归配置，版本归分支，验证归任务，审查归 Codex。**

## 推荐的项目分层

### 第 1 层：产品族核心层

放真正长期复用的内容：

- 保护策略
- `SOC`
- 低功耗状态机
- 协议核心
- 公共算法
- 工具链
- `host_sim`
- 回归脚本

这层应该尽量做到：

- 不直接依赖具体 `MCU / AFE / GPIO`
- 可被 `PC` 仿真
- 可被 Codex 回归和审查

### 第 2 层：平台适配层

放板级和芯片差异：

- `MCU` 差异
- `AFE` 差异
- `ADC / GPIO / RTC / 中断 / UART / I2C`
- `BSP`
- 引脚映射

这层的职责是把硬件差异挡在边界上，不让它们污染核心逻辑。

### 第 3 层：客户配置层

放客户差异：

- 参数
- 功能开关
- 协议小差异
- 型号信息
- 客户约束

这层尽量避免写成大量 `#ifdef CUSTOMER_A / CUSTOMER_B` 散在业务代码中。

更推荐：

- 配置表
- feature flag
- 参数文件
- 模板变量

## 推荐的仓库与项目组织方式

如果你的项目数量多，而且核心逻辑重复度高，长期最稳的方向是：

### 方案 A：一个核心模板仓库 + 多个项目仓库

适合你当前阶段。

结构建议：

- 当前这个仓库逐步演进为“模板 / 核心工作流仓库”
- 新项目从模板生成
- 每个正式项目仍有自己的仓库

优点：

- 风险可控
- 不会一下切到复杂 monorepo
- 更容易逐步把老项目迁移进来

### 方案 B：产品族仓库 + 多板型配置

适合后续更成熟时再做。

也就是一个仓库里同时管理：

- 共性核心
- 多个平台实现
- 多客户配置

这个方向更强，但前提是你先把边界和配置体系收紧。

以你当前状态，我建议先走方案 A。

## 推荐的版本线模型

对每个项目，建议固定至少这 4 条线。

### 1. 稳定出货线

示例：

- `release/project-a`
- `release/project-b`

职责：

- 当前出货版本
- 只接收必要修复
- 保守优先

### 2. 研发主线

示例：

- `develop/project-a`
- `develop/project-b`

职责：

- 新功能
- 新硬件适配
- 长期重构
- 方案探索

### 3. 热修复线

示例：

- `hotfix/project-a-yyyymmdd-issue`

职责：

- 从稳定版切出
- 修线上问题
- 最小改动

规则：

- 修完后必须回并到 `release`
- 同时必须回并到 `develop`

### 4. Codex 工作线

示例：

- `codex/protection-sim`
- `codex/soc-replay`
- `codex/customer-config-cleanup`

职责：

- 承接 Codex 的局部实现
- 承接 Codex 的工具链和回归建设
- 不直接长期承担产品版本责任

## 客户差异的管理方法

客户差异建议分成 3 类来管。

### A. 参数差异

例如：

- 保护阈值
- 容量
- 温补参数
- 校准参数

管理方式：

- 单独配置文件
- 参数表
- 模板变量

### B. 功能差异

例如：

- 某客户启用某协议扩展
- 某客户关闭某种保护上报

管理方式：

- feature flag
- 构建选项
- 配置开关

### C. 硬件差异

例如：

- `MCU` 不同
- `AFE` 不同
- IO 定义不同

管理方式：

- 平台适配层
- 驱动实现层
- 板型配置

**不建议的做法**

- 一个客户复制一份完整代码长期各自演化
- 客户差异到处散落在 `if/else` 和 `#ifdef` 中
- 热修复只改稳定版，不回流研发版

## 适合你个人的最小工作流

你不需要先学完整的大团队 GitHub 流程，先用下面这套最小动作就够了。

### 日常开发

1. 从对应项目的 `develop/<project>` 切工作分支
2. 做改动
3. 跑标准验证：
   - `task build`
   - `task sim-protection-suite-summary`
4. 让 Codex review 当前改动
5. 确认后合并回 `develop/<project>`

### 线上热修

1. 从 `release/<project>` 切 `hotfix/<project>-...`
2. 最小改动修复
3. 跑最小必要回归
4. 合并回 `release/<project>`
5. 再合并回 `develop/<project>`

### 新客户派生

1. 不复制整个项目去野化演化
2. 优先增加客户配置
3. 必要时增加少量平台适配
4. 保持核心逻辑尽量共用

## Codex 在你工作流中的角色

对你来说，Codex 最有价值的不是“陪聊”，而是承担下面这些重复但高风险的工作：

### 1. 修改前分析

Codex 先帮你判断：

- 这次改动属于哪条版本线
- 会影响哪个客户 / 哪个板型
- 应该走热修还是研发线

### 2. 修改与工具链维护

Codex 帮你：

- 改代码
- 改任务入口
- 改文档
- 改回归场景

### 3. 自动验证

Codex 帮你执行：

- `task build`
- `task sim-*`
- 摘要生成
- 构建 / 仿真 / 回归结果解释

### 4. 第一轮审查

Codex 帮你判断：

- 有没有跨平台问题
- 有没有版本回流遗漏
- 有没有客户差异误伤
- 有没有保护 / `SOC` / 低功耗回归风险

## 为什么 PR 对你也有意义

你一个人也可以用 `PR`，而且很有意义。

对你来说，`PR` 不主要是给别人看，而是：

- 给未来的你自己看
- 给 Codex 审查
- 给版本流转留记录
- 给热修回流提供依据

你可以把 `PR` 先理解成：

**“准备把一批改动并入正式版本前，先做一次变更审查和留档。”**

## 适合你个人的 PR 使用方式

最简版可以这样用：

1. 在工作分支完成改动
2. 跑：
   - `task build`
   - `task sim-protection-suite-summary`
3. 发起 `PR`
4. 让 Codex 做第一轮 review
5. 通过后再合并

即使只有你自己，这也有价值，因为它能：

- 降低误合并风险
- 让热修和研发流转更清晰
- 让每次改动带验证记录

## 你现在最该先建立的习惯

先不要追求一次把所有项目都重构成完美体系。

建议先建立下面 5 个习惯：

1. 所有改动先分清是 `release / develop / hotfix / codex`
2. 客户差异优先放配置，不优先复制代码
3. 每次核心改动都跑 `task build` 和 `task sim-protection-suite-summary`
4. 让 Codex 做第一轮 review
5. 热修一定回流研发线

## 建议的近期落地顺序

### 第 1 阶段：把当前仓库变成模板仓库

目标：

- 稳定 Win/Mac 工具链
- 稳定 `task` 入口
- 稳定保护回归
- 稳定 Codex 审查入口

### 第 2 阶段：把客户差异逐步配置化

目标：

- 从“代码拷贝差异”变成“配置差异”

### 第 3 阶段：把 `SOC` 和低功耗也做成可回归资产

目标：

- 让 Codex 不只会看保护逻辑，还能看精度和功耗策略

### 第 4 阶段：把项目族管理方法固化

目标：

- 新项目直接复用这套模式
- 老项目逐步迁移

## 当前最适合你的结论

你真正需要的不是“学会某个 GitHub 功能按钮”，而是这套结构：

- 共性核心
- 平台适配
- 客户配置
- 稳定版 / 研发版 / 热修版
- Codex 负责第一轮实现、回归、审查、总结

这才是一个人长期维护很多相似嵌入式项目，不失控的办法。
